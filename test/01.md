# Architecture Refactor Progress Report

The project has now transitioned from a simple command-oriented plugin system into an event-driven runtime architecture designed for future AI orchestration and extensibility.

## Major Architectural Improvements

### 1. Domain Event Taxonomy

A typed event system was introduced with domain-specific events:

* filesystem events
* search lifecycle events
* edit proposal/apply/reject events
* AI suggestion and approval events
* user intent events
* tab lifecycle events

This establishes a consistent runtime communication model.

---

### 2. Shared Runtime Context

A centralized AppContext service now provides:

* namespaced state access
* shared runtime memory
* change listeners
* reactive state coordination

This creates a stable foundation for orchestration and AI-aware workflows.

---

### 3. Intent Pipeline

The architecture now separates:

* intents
* actions
* events

Intents represent lifecycle-aware requests processed through middleware and hooks.

This enables:

* validation
* orchestration
* approval flows
* AI intervention
* future safety systems

without tightly coupling plugins.

---

### 4. Event-Driven Plugin Communication

Plugins can now subscribe globally through:

```ts
onAny()
on('*')
```

This enables decoupled runtime observers such as:

* AI orchestrators
* logging systems
* telemetry
* debugging tools
* replay systems

---

### 5. AI-Oriented Edit Pipeline

Editing was redesigned into a proposal-based workflow:

```text
AI -> propose diff -> approval -> apply
```

This prevents uncontrolled mutations and establishes a safe human-in-the-loop editing model.

---

### 6. Diff Infrastructure

A dedicated diff engine now supports:

* line-level changes
* unified diff generation
* edit proposal visualization

This creates a strong foundation for future collaborative and AI-assisted editing.

---

### 7. Runtime Orchestration Layer

The introduction of orchestrators formalizes system coordination responsibilities.

AI behavior is now evolving from a direct command executor into a planning/orchestration participant.

---

## Architectural Direction

The project is evolving toward:

* event-driven runtime architecture
* AI-native workflows
* decoupled plugin ecosystems
* observable execution pipelines
* suggestion/approval-based editing systems

rather than a traditional command-only plugin application.

---

## Important Next Steps

The next architectural priorities should include:

### Event Metadata Standardization

Introduce canonical event envelopes:

```ts
{
  id,
  type,
  timestamp,
  source,
  correlationId,
  causationId,
  payload
}
```

This is important for:

* tracing
* debugging
* replay
* AI reasoning
* execution history

---

### Intent State Machines

Formalize lifecycle transitions:

```text
pending
processing
waiting-approval
approved
rejected
completed
failed
```

---

### Event History / Replay

Introduce lightweight event persistence to support:

* debugging
* runtime replay
* AI memory
* audit history
* crash recovery

---

### Runtime Observability

A timeline/debugger view should eventually visualize:

* intents
* emitted events
* plugin reactions
* AI proposals
* approvals
* state transitions

---

## Overall Assessment

The architecture is now moving away from a fragile command-based structure toward a much more scalable and AI-compatible runtime model.

The current direction is strong, modern, and aligned with systems designed for AI-assisted orchestration rather than simple plugin execution.
